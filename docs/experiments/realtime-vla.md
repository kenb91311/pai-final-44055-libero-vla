# SmolVLAとπ0-FAST：実時間でaction chunkを実行する

## 目的・課題設計

2026-11-02。検証する問いは「同じ物理制御周期・chunk実行条件で、軽いモデルの低遅延がタスク結果にどう表れるか」。タスク適応済みVLAを、認識・ROS通信・物理制御へ接続し、物理停止の基準実行と実時間実行を比較する。既存の課題適応済みモデルを実時間システムとして動かすことが主題である。

LIBERO-Spatialのtask0「皿とラメキンの間の黒いボウルを拾い、皿へ置く」を選択。両モデルにLIBERO用公開済み重みがあり、Panda・2視点RGB・7D相対手先行動の契約を共通化できる。独自の形状や床球技へ転用するより、学習なしで動く条件を確認しやすい。

## 正式評価の条件を先に固定

機械可読条件：`artifacts/realtime-vla/formal-protocol.json`。開発state0と正式state1〜5を分離。モデル2種類×条件2種類×初期配置5種類=20episodes。各モデルは単独でGPUへ常駐させる。

| 項目 | 条件 |
|---|---|
| 物理制御 | 公式LIBEROの20Hz、MuJoCo物理dt 0.002s |
| センサ | 外部・手首RGB256×256、自己状態8D。実時間側カメラ10Hz |
| タスク予算 | 14秒。lockstepは280物理step、実時間は14壁時計秒または280step |
| 生成/実行chunk | SmolVLA生成50、π0-FAST生成10。主比較は両者先頭10のみ実行 |
| 要求タイミング | queue残量0で次chunk要求、FIFO、同時に1要求 |
| queue枯渇 | 差分位置/姿勢0、グリッパ指令維持 |
| 初期化 | seed20261102、公式保存初期状態、2回warmup、初回chunk事前計算 |
| 通信 | 全正式試行でROS 2の画像・自己状態・chunk往復を使用 |
| 成功 | LIBERO公式predicate。XY距離だけで代用しない |
| 重み | 凍結。追加学習なし。実行前後digest一致 |

lockstepは同期カメラで物理を止めて推論する。実時間側は同一snapshotから別プロセスでカメラを生成する。両者の差はシステム構成込みであり、純粋にモデル推論時間だけの因果効果とは主張しない。データセットmetadataのfps10と、公式環境のcontrol20Hzも区別する。

## 試行錯誤と切り分け

| 問題 | 試したこと・原因 | 得られた知見/採用した対応 |
|---|---|---|
| SmolとFASTの依存APIが合わない | 古いLeRobot版とFAST用transformers forkはSmolとの同居が難しい | 両APIを備えるLeRobot mainの同じcommit、専用環境を固定 |
| 公開重みなのにFASTのtokenizerが取得できない | Gemma tokenizerの取得経路の制約 | 公式に公開されたPaligemmaのSentencePieceを使い、語彙IDと特殊tokenを検証 |
| 読込み失敗を見落とす危険 | 上流FAST loaderは例外を捕まえて初期化モデルを返す経路がある | constructorと公式key変換後にstrict load。604tensorの復元を確認 |
| 同期描画では20Hzが出ない | デフォルトCPU llvmpipe、NVIDIA D3D12でも画像2枚込み平均85.64ms | 画像なし物理は8.98ms。snapshot cameraを分離し20Hzを維持 |
| 別カメラが正しい場面か | 物理cloneと同期環境を比較 | 同じsnapshotの画像と自己状態が全バイト一致 |
| 古い画像を新しい時刻と誤認する | 推論送信/完了時刻を観測時刻へ代用するとageを過小評価 | snapshot取得時刻を保持。初回warmup後は再取得し、bootstrap/steadyを分ける |
| 遅いモデルの待機中に移動が暴走する | 相対actionの最終値反復は停止にならない | 6軸ゼロ差分+グリッパ維持。holdを失敗として隠さず計測 |
| 非同期推論が本当にROSを使うか | メタデータだけの往復では不十分 | 受信済みの画像・chunkを使い、送受信ハッシュを毎回検証 |
| 同じ初期状態なのに方式間で画像hashが違う | robosuite stepは周期観測cache、snapshot描画はforward後に強制更新。観測位相が異なる | 同方式のモデル間は初期sensorが完全一致。方式間の初期物理状態は一致するが、モデル遅延だけを分離した比較とは扱わない |

環境構築詳細は `artifacts/realtime-vla/environment-build-notes.json`、カメラ測定は `environment-smoke/`。単体テスト18件成功。これらのテストをタスク成功の代用にはしない。

## 開発試行（正式成績に混ぜない）

state0・E10・prefetch0で、物理停止の基準はSmolVLA79action、π0-FAST80actionで成功。実時間Smolは163ticks・8.14秒・hold50.9%で成功、π0-FASTは280ticks・14秒で未成功、hold67.9%。両者のRTFは約1.00で、カメラ・ROS・推論の待機中も物理を進められた。初回観測にはwarmupが含まれる古さの偏りがあり、正式評価前に撮り直す修正を入れた。state0だけから成功率・精度順位は結論しない。

## 正式評価結果

元データは `artifacts/realtime-vla/formal-{smolvla,pi0fast}-e10/`。初期状態1〜5の各5試行、エラー0、全ROS往復の送受信hash一致、全重み前後不変。

| モデル・方式 | 公式成功 | 終端XY中央値 | ROS込みworker時間 | 待機tick割合 | 実時間比中央値 |
|---|---:|---:|---:|---:|---:|
| SmolVLA / lockstep | 5/5 | 24.1mm | 615ms | 0% | 0.354 |
| SmolVLA / realtime | 3/5 | 29.9mm | 604ms | 53.2% | 0.998 |
| π0-FAST / lockstep | 4/5 | 12.0mm | 1000ms | 0% | 0.290 |
| π0-FAST / realtime | 1/5 | 125.3mm | 1018ms | 66.7% | 1.003 |

worker時間は各episodeの通常chunk平均を5episodeで平均した値。bootstrapを除き、終了後に完成して適用されなかったchunkも計算時間へ含む。センサROS→モデル→chunk ROSを含み、親IPC/poll待ちは含まない。純GPU kernel時間ではない。通常行動の観測→適用ageはRTでSmol938ms、π1409ms。両者の最新camera ageは約188msで同程度だった。

実測control周波数はSmol約19.92Hz、π約20.00Hz。RTFは初回tickを即実行する境界のため僅かに1を超える場合もある。lockstepのRTFを実時間制御成功として扱わない。全5配置の個別成功・失敗を公開し、成功映像だけから成功率を推定しない。

この条件では、Smolはより低い生成遅延・指令元ageと、より多い実時間成功・小さい終端誤差を示した。ただし静的成功率も異なり、純粋なモデル遅延だけの効果とは断定できない。πはlockstepの終端XY中央値が小さい一方、公式成功数はSmolより少ない。「精度」の指標を一つにまとめない。

## 解釈の範囲

モデルのサイズ・tokenizer・学習レシピ・生成長も異なるため、速度差をパラメータ数だけで説明しない。待機actionが多いこと、画像の古さ、最終XY誤差、controller追従誤差は別の指標。5初期配置の小標本であり、LIBERO全体や未知物体の優劣とは扱わない。推論過程を止めずに制御するsoft realtimeの測定であり、desktop OS上のhard realtime保証ではない。

## 追加検証：先読み条件

`artifacts/realtime-vla/ablation-protocol.json` に主評価と別の探索的条件を保存した。両モデルとも同じ5初期配置で、残量5時点に次chunkを要求する（prefetch5）。その他はE10・20Hz・カメラ10Hz・14秒・ROS・FIFOを維持。先読みなしの20試行を置き換えない。同じ初期配置の再利用であり、新たな未使用test集合とも呼ばない。

先読みなしでは、chunkを使い切ってから約0.5〜1秒の推論を行うため、queue枯渇が構造的に生じる。一方、先読みすると古いchunkを実行している途中の観測で次chunkを生成する。待機率が下がっても動作の整合が改善するとは限らない。今回の単純FIFO先読みは遅延を条件にしたinpainting/RTCではない。

結果はSmolVLA・π0-FASTとも0/5成功。待機tickはSmol40.4%、π58.6%へ減少したが成功は増えなかった。両モデルの全5状態を保存し、改善する例だけを選別していない。

## 追加検証：生成50全実行の条件

`native-horizon-protocol.json` を実行前に保存し、Smolの生成50をすべて実行するE50・先読み0を同じ5状態で試した。E10と比較して成功数は3/5のまま。成功状態はE10が1・2・5、E50が1・3・4で入れ替わった。待機が約16%まで下がっても、全体成功数は改善しなかった。長いopen-loop実行で視覚による修正頻度が下がることと、待機短縮の両面がある。保存configの標準消費長1を、50へ読み替えたものではなく、外部schedulerの探索的条件である。

πの生成長10を変えていないため、E50をSmolとπの同一実行条件比較へ混ぜない。先読み・全生成長の追加計15試行は、主比較20試行と別に報告する。
